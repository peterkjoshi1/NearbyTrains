NearbyTrains

See which trains are near you, right now.

NearbyTrains shows your nearest Scottish National Rail stations on a live map, with upcoming departures at a tap. Drop a pin anywhere to see which trains will pass that spot in the next hour. Watch trains move in real time with arrows showing their direction of travel.

User guide

These instructions assume you are running on a Mac with Xcode and using the iOS Simulator.

One-time setup

Python dependency

pip install stomp.py

Network Rail credentials

Register for a free account at publicdatafeeds.networkrail.co.uk, then create the credentials file:

mkdir -p ~/Library/Application\ Support/NearbyTrains
cp server/credentials.example ~/Library/Application\ Support/NearbyTrains/credentials

Edit the file and fill in your Network Rail username and password.

API tokens

Copy Secrets.xcconfig.example to Secrets.xcconfig in the project root and fill in:

  • Mapbox public token — from account.mapbox.com
  • RTT refresh token — from api-portal.rtt.io

Starting the server

Open a terminal and run:

cd /path/to/NearbyTrains
python3 server/train_tracker.py

Healthy startup output looks like:

[LEARN]  Loaded 1,171 learned berth coordinates
[HTTP]   Listening on http://localhost:8080
[STOMP]  Connected — subscribed to TD_SE_SIG_AREA, TD_SW_SIG_AREA, TRAIN_MVT_ALL_TOC
[STATS]  trains=0 (0 located) | STOMP msgs=0 ...

Within 30 seconds the stats line should show trains being tracked. To monitor it continuously in a second terminal:

watch -n 5 'curl -s http://localhost:8080/trains/stats | python3 -m json.tool'

The server must keep running while you use the app. It reconnects automatically if the Network Rail feed drops.

Running the app

  1. Open NearbyTrains.xcodeproj in Xcode
  2. Select an iPhone simulator from the device picker (iPhone 15 or later recommended)
  3. Press Cmd+R to build and run
  4. The map opens centred on Scotland. Stations appear as blue dots within a few seconds. Train markers appear once the server has data — allow 30–60 seconds after starting the server for the first positions to arrive.

Note: the simulator runs on your Mac and can reach localhost:8080 directly. On a physical device, update the IP address in NearbyTrains/TrainPositionService.swift to your Mac's local network IP.

Using the app

The map

Railway lines are highlighted in red. Blue dots mark stations within range. Train positions update every 10 seconds.

Station departures

Tap any blue station dot. A sheet slides up showing the next departures from that station — destination, scheduled time, expected time, and platform if known. The dot turns orange while selected.

Live train positions

Trains appear as coloured arrows (direction known) or dots (direction not yet known). Colour indicates how recently the position was updated:

RedUpdated in the last 90 seconds
Amber1 to 5 minutes since last update
Grey5 minutes to 1 hour since last update — typically a Highland train between stations

Tap a train marker to see its headcode, route (origin → destination), berth, distance, and how long ago it was last seen. If the route cannot be determined automatically — for example, an express that does not stop at nearby stations — a Look up on RTT link opens the Real Time Trains website for that service.

Passing train forecast

Long-press anywhere on the map (hold for half a second). A red pin drops and a sheet appears listing trains scheduled to pass that point in the next hour, sorted by time. This works by finding the two nearest stations to the pin and fetching their departure boards.

Limitation: express trains that pass through without stopping at either of the two nearest stations will not appear in the forecast.

Highland trains

Trains on the Highland Mainline, Far North Line, West Highland Line, Kyle and Oban lines appear as grey dots updated only when the train passes a station — typically every 20 to 40 minutes. This is a data source limitation; see Geographic coverage for the full explanation.

What it does

Tap a station to see departures

Station locations are loaded from OpenStreetMap and shown as blue dots. Tap one and a sheet slides up showing the next two departures — destination, scheduled time, expected time, and platform if available. The dot turns orange to show it is selected.

Drop a pin for a passing train forecast

Long-press anywhere on the map to drop a red pin. The app finds the two nearest stations to that point, fetches all services scheduled in the next hour, deduplicates across both stations, and presents them sorted by time. Useful if you are at a bridge, level crossing, or anywhere along a line.

Limitation: the forecast is built from timetabled calls at nearby stations. Express trains that pass through without stopping at either of the two nearest stations will not appear, even if they run right past the pin.

Watch live train positions

Every 10 seconds the app polls a local server connected to Network Rail live data feeds. Each train appears on the map at its current position. Trains with a known direction of travel show as arrows; trains with only one position recorded show as plain dots. Colour indicates freshness:

RedPosition updated in the last 90 seconds
Amber1 to 5 minutes since last update
Grey5 to 15 minutes since last update
Grey5 minutes to 1 hour since last update — typical for Highland trains between stations

Railway lines on the map

The Mapbox Streets style contains railway geometry. The app highlights those lines in red so the track layout is clearly visible alongside the live train positions.

How it works

Train positions are not GPS

The live positions come from the same signalling data that train controllers use — a system called Train Describer, or TD. The track is divided into sections called berths. Every time a train moves from one berth to the next, a message fires. The server receives those messages in real time, typically within two or three seconds of the train moving.

The challenge is that berths are a signalling concept, not a geographic one. They have names like ED:L451 but no published coordinates. To place a train on a map, the server works through a chain of lookups: first it checks whether the berth is near a known station, then whether that station has a coordinate. For trains near stations this usually resolves quickly. For trains in the middle of a long rural section between stations, there is often nothing to look up — and the train appears stuck at its last known position until it reaches the next resolvable berth.

How a train gets placed on the map — three lookups, each with a fallback if nothing matches.

Learning positions between stations

To fill those gaps the server runs a self-learning system. A second feed called TRUST fires whenever a train passes a known reporting point — typically at a station. By recording the exact wall-clock time a train passed two known locations, the server can estimate where that train was at any moment in between, by assuming it travelled at constant speed between the two points.

Every time it makes one of these estimates for a berth that had no coordinates, it stores it. Once it has seen five consistent estimates for the same berth, that position is saved permanently in a local database. The next time a train enters that berth the coordinate is available immediately. The database persists across server restarts, so coverage only grows over time — after a day of normal service, several hundred berths will have learned coordinates.

Limitation: the estimate assumes straight-line, constant-speed travel between the two bracketing stations. On curved approaches — Glasgow city lines, Edinburgh Waverley throat — the estimated position drifts slightly away from the actual track.

How the server learns a position for a signal section it has never seen before — each estimate is saved immediately, but 5 are needed before the result is trusted for live use.

Server and app

A Python server runs locally, maintains the STOMP connections to Network Rail, resolves positions, and exposes a simple REST API on port 8080. The iOS app polls /trains every 10 seconds and updates the map. Station departure data comes from the Real Time Trains API directly from the app.

Data feeds

Network Rail TD STOMP feed

The server subscribes to TD_SE_SIG_AREA (Scotland East) and TD_SW_SIG_AREA (Scotland West) on the Network Rail Open Data STOMP broker. Each message is a JSON array of Train Describer events. The server uses CA_MSG (berth step) events, which fire every time a train moves from one signalling berth to the next.

[{
  "CA_MSG": {
    "area_id": "ED",
    "descr":   "2N53",
    "from":    "L451",
    "to":      "L453",
    "time":    "1745920800000"
  }
}]

descr is the headcode. area_id identifies the Train Describer area. to is the berth the train has just entered. Timestamp is milliseconds since epoch.

Network Rail TRUST STOMP feed

On the same STOMP connection, the server also subscribes to TRAIN_MVT_ALL_TOC. TRUST fires a TRAIN_MOVEMENT event every time a train passes a reporting point. Events are filtered to Scottish STANOX prefixes (03–09). TRUST events serve as geographic anchors for the berth learner.

{
  "header": { "msg_type": "0003" },
  "body": {
    "train_id":         "881D42ME29",
    "loc_stanox":       "07259",
    "actual_timestamp": "1745921340000"
  }
}

Headcode is extracted from train_id[2:6]. The STANOX is resolved to a lat/lon via CORPUS and the coordinate cache, then stored as a timed anchor for that headcode.

SMART data

SMART (Sectional Map of Allocated Reporting Timetable) maps berth steps to STANOX location codes. Loaded at startup from smart_data.json. Contains 22,333 Scottish berth entries. For each CA_MSG berth step, SMART provides the corresponding STANOX (if known).

CORPUS data

CORPUS maps STANOX codes to CRS station codes. Loaded at startup from corpus_data.json (3,128 mappings). Once a STANOX resolves to a CRS, coordinates can be looked up from the coordinate cache.

Coordinate cache

A persisted JSON file (coord_cache.json) maps CRS codes to WGS-84 coordinates, populated on demand by Overpass API queries. Seeded at startup with static coordinates for key Scottish stations.

RTT API

Station departure boards come from the Real Time Trains API. The app exchanges a refresh token for a short-lived access token, then queries /gb-nr/location?code={CRS} for each selected station.

OpenStreetMap

Station coordinates are fetched via the Overpass API, querying for nodes tagged railway=station with a ref:crs tag within a bounding box around the user's location.

Geographic coverage

Central belt — live continuous tracking

The Scottish central belt and East Coast corridor are covered by Network Rail's TD STOMP feed. The server subscribes to TD_SE_SIG_AREA and TD_SW_SIG_AREA, which carry berth-step messages for TD areas EA, EB, EC, ED, G1, G2, YO, SM and others. This covers:

  • Edinburgh and surroundings — all suburban lines, Waverley, Haymarket
  • Glasgow and surroundings — Queen Street, Central, all suburban lines
  • East Coast corridor — Dunbar north through Dundee to Aberdeen
  • Cross-country — Stirling, Falkirk, Fife, Dunblane, Perth

On these lines trains generate a berth-step message every few seconds as they move, giving near-real-time positions.

Highland and remote lines — no TD coverage

The following routes carry no TD berth data in the public Network Rail feed:

  • Highland Mainline — Stirling → Perth → Aviemore → Inverness
  • Far North Line — Inverness → Dingwall → Tain → Wick and Thurso
  • West Highland Line — Glasgow → Crianlarich → Fort William → Mallaig
  • Kyle of Lochalsh Line — Dingwall → Kyle
  • Oban branch — Crianlarich → Oban

These lines use RETB (Radio Electronic Token Block) signalling — a radio-based single-line token system designed for remote routes with light traffic. RETB does not generate track circuit berth messages, so there is nothing for the TD system to publish. The TD area codes for these routes exist in Network Rail's SMART reference data (areas IH, IN, IR, CV, AD) but do not appear in any public STOMP topic, including the combined TD_ALL_SIG_AREA feed.

A note on apparent Highland sightings: early in development some Glasgow-area berths showed positions in the Highlands — Thurso, Caithness — due to headcode reuse. The same four-character headcode is sometimes reused for different services in geographically distant areas on the same day. This caused coordinates from the Far North Line to be incorrectly learned against Glasgow berths. The server now detects these jumps (>100 km between successive position fixes for the same headcode) and discards the contaminated data.

Planned: TRUST snapshot positions for Highland trains

The TRUST feed (TRAIN_MVT_ALL_TOC) does cover Highland trains — it fires a movement event whenever a train passes a timing point, typically a station. The server already receives these events and uses them to help the berth learner in the central belt.

The planned next step is to use TRUST events directly to place Highland trains on the map. A train would appear at Stirling, then Perth, then Pitlochry, then Aviemore, updating each time it passes a timing point. The position would not move smoothly between stations — but it would show the correct last-reported location, which is far more useful than nothing.

Known limitations

Train positions are signalling berths, not GPS

The Train Describer system was designed for signallers, not passengers. Position is inferred from which berth a train occupies. Long stretches between significant berths have no position updates — trains appear stuck at their last resolved berth until they reach the next one. The age_seconds field in the API indicates staleness; the app hides trains silent for more than 15 minutes.

Planned improvements

TRUST-based Highland tracking: Use TRUST timing-point events to show Highland trains at their last reported station, even without TD berth coverage. See the Coverage section above.

Snap-to-rail: Interpolated and SMART-derived berth coordinates are point estimates, not constrained to the actual track geometry. Pre-downloading Scottish railway geometry from OSM and projecting positions onto the nearest line segment would improve accuracy on curved sections.

VectorLinks: Network Rail VectorLinks provides actual track geometry as linestrings. Combined with timetable data, a train's position could be interpolated along the real curve based on elapsed time, making trains appear to move smoothly between known positions.

Community berth maps: The List of Train Describers wiki has user-contributed berth maps for Scottish TD areas. Incorporating these would immediately improve SMART coverage for berths not in the official dataset.

Technical

  • SwiftUI iOS app (iOS 17+), @Observable, UIViewRepresentable wrapping Mapbox Maps SDK v11
  • Python server (train_tracker.py) — single STOMP connection to Network Rail Open Data, handling TD (Scotland E+W) and TRUST (national) feeds via one CombinedListener
  • Position chain: SMART (22,333 berths) → CORPUS (3,128 STANOX→CRS) → coordinate cache (JSON, Overpass-populated) → berth learner
  • Berth learner (berth_learner.py) — SQLite-backed self-populating coordinate database; linear time interpolation between TRUST anchors; 5-observation convergence threshold
  • Reconnection: exponential backoff (60 s → 30 min cap); heartbeats every 10 s to prevent broker TTL drops; AMQ339009 session-wait handling
  • Station departures from RTT API; nearby stations from OpenStreetMap Overpass API
  • REST API on port 8080: /trains, /trains/stats, /trains/debug
  • Bearing calculated server-side from consecutive berth positions; rendered as rotatable arrow annotations on the map
